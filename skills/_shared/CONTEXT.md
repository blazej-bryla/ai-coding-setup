# Context budget — what lands in the orchestrator

The session that holds the gates (`/work`, `/bugfix`, `/deslop`) keeps its context for judgment, not dumps. These rules change only how much output reaches it — never which gates run, what is reviewed or what is verified. The last four bullets (Evidence, Causes, Repair cap, Cold reader) are shared working rules for every skill that points here. Resolve `~` to the absolute home directory.

- **Pass/fail commands** — tests, lint, typecheck, build: `~/.agents/bin/quiet [-C <dir>] "<command>"` (or `quiet <command> <args…>`). Green → one line `ok: <cmd> (<n>s)`; red → `FAIL (exit N)` and the last 40 lines (`-n 80` when 40 don't show the first error). `-C` = run in that directory (a worker's worktree root). It runs only package/test/lint/build tools and refuses shell syntax — never put git, gh or a pipe through it.
- **git push** — `git push --quiet <args> 2>&1 | tail -20`; a failure shows in those lines (`rejected`, `error:`, a hook's last lines). The user's `ask` on push still applies.
- **Browser** — `~/.agents/bin/abcheck <session> <url> '<expectation>' <shot.png>` (options: `--freeze`, `--full`, `--shot-only`, `--diff <base.png> <out.png>`; `-` for no expectation / no shot). It runs ONE agent-browser batch in the task's session with the saved login (`--state ~/.agent-browser/auth-base.json --restore`): `set viewport 1440 900`, `console --clear`, `errors --clear`, `network requests --clear`, `open <url>`, `wait --text '<expectation>'` (no expectation → `wait --load networkidle`), `console`, `errors`, `network requests --status 400-599`, `eval` (title, URL, password field, page text), `screenshot <shot.png>` — and prints one line per check: `PASS|FAIL expectation`, `console errors: N`, `page errors: N`, `failed requests: N` (status, method, URL), then `page:` (title — URL), `login form: yes` when the page has a password field, `text:` (first 300 characters, only when the expectation is missing), `shot:`, `diff:`, `verdict: pass|fail` (exit 0 / 1; 3 = agent-browser itself failed, its last 20 lines shown). Closing the session: `agent-browser --session <session> close` — never `close --all`. Those are the only agent-browser commands these skills use: never run `agent-browser --help` or `agent-browser skills …` in a session. **Never Read a screenshot** unless a check failed or the user asks — screenshots are for the PR and the user.
- **Worker hand-backs** — a `wf-implementer` returns ≤ 40 lines (status, branch, worktree, report path, commits, files as paths, `deps:`, `tests:`, `acceptance:` — one mark per criterion — and `easy-to-miss:`, `open:`, `outside-scope:`, `friction:`, `deviation:`); its full report is at `~/.agents/scratch/<slug>/reports/<id>.md`. Read the full report only when `status` is `blocked` or `partial`, or `open`, `deps:` or `deviation:` is not `none` — and then the sections you need. Of the acceptance lines, act only on items not marked `proven` / `followed` (see Evidence).
- **Repo questions** — "how does X work", "where is Y", "what calls Z" go to a `wf-explore` subagent; its synthesis comes back, the files don't. In this session: Read with `offset`/`limit` on the lines you need, `grep -l` (or `grep -n -m 5`) to locate — never `cat`, `sed -n`, `head`/`tail` on source files, never `grep -A/-B/-C` over the repo. A file you are about to edit is still read in full first.
- **Scratch files** — `context.md` / `spec.md` once at the start; afterwards only the section a ticket or finding points to (Read with `offset`/`limit` at that heading). Tickets: `~/.agents/bin/tickets` for the one-line-per-ticket listing; a ticket file in full only when it is being landed. Review: the summary block at the top of `review/findings.md` (`sed -n '1,/^<!-- \/summary -->/p' <findings.md>`); a finding in full (its `## #N` section) only when you act on it.
- **Diffs** — `git diff <range> --stat` by default; the full diff only for the files a finding, the teach brief or a decision points to (`git diff <range> -- <path>…`).
- **Evidence** — a worker's or reviewer's claim counts only with evidence that happened in this session: a `quiet` `ok:` line or its failing output, an `abcheck` `PASS` line, or a file path. An unrun check is never inferred as passing. Acceptance marks: `proven — <evidence>` | `not proven — <gap>` | `changed — <new requirement>. Reason: <what changed it>`; the ticket's Easy-to-miss rule: `followed — <evidence>` | `broken — <how>` | `not proven — <gap>`. For each item not `proven` / `followed`, decide one of three: check it yourself, send it back to the worker, or ask the user with the reason. Everything proven moves on to review.
- **Causes** — state problems as observed, with evidence. Name a cause only when you verified it and say how; label a guessed cause as a guess. This holds for hand-offs, repair briefs and messages to the user.
- **Repair cap** — per ticket (or per fix in `/bugfix`, per thread in `/address-review`): one repair and one re-review. A second blocking result ends the loop: report what remains, what it cost (repairs run, rough minutes), and ask the user — no third attempt on your own.
- **Cold reader** — the user may come back after a long gap. A question or gate message starts with one or two lines of state — task, ticket, what happened since their last message — then the question. The reply is as big as the question.
